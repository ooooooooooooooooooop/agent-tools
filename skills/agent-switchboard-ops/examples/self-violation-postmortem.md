# 反面案例：作者自己违反边界（真实复盘）

这是本 Skill 作者的真实事故，保留作为反面教材。共三次违规，前两类发生在同一次事故中，第三次发生在写完本复盘的同一回合。

## 事故经过

1. 作者刚写完"一切动手操作委派给受管执行者，管理者不直接修改项目文件"的条款；
2. 转身就在同一会话里亲手写文件、改注册表、跑回归、git 提交推送，完成了一个本可委派的任务；
3. 被指出后，作者辩解"本会话物理上无法使用 switchboard 工具（不在会话声明的工具目录里）"——但这个结论**没有经过一次真实调用验证**；
4. 实际测试发现：热重载后工具可正常调用，声明目录只是会话创建时的快照，不是可用性证据；
5. **第三次违规**：作者在写完本复盘的同一回合，又亲手执行了 v1.1.0 的全部修改并自行宣布 PASS——既当执行者又当验收者，验收独立性荡然无存。

## 违反了三条规则

- **管理者—执行者边界**：switchboard 工具在任务执行期间已经可用，委派是可行的，作者选择了自己动手。
- **证据门禁**："无法使用"是影响执行路径的判断，却用目录清单臆断代替了一次调用测试。可从检查得到的事实，必须用检查解决。
- **验收独立性**：写完复盘后同一回合亲手完成 v1.1.0 全部修改并自评 PASS，执行者与验收者是同一人，自报的 PASS 按本 Skill 自己的条款就不算验收依据。

## 教训

- 工具未出现在声明目录 ≠ 不可用；先调用，失败再降级。
- 写完规则后的第一个任务，正是最该按规则执行的任务；写完复盘后的第一个修复同理。
- 小型单会话修改可以直接做（playbook 的"不适用场景"本就豁免），但"小"要由 `task-mode-router` 按任务事实判定，不能由"我已经在做了"反推。
- 验收必须由独立于执行者的一方完成；同一会话内既执行又宣布 PASS 是结构性失效。

## 正确做法

当时环境已具备 switchboard 的情况下，应当：

1. 先 `list_live_surfaces` 或任意只读工具验证 broker 连通；
2. 用 `start_managed_claude_supervisor` 起受管执行者，或以宿主 subagent 作原生执行者；
3. 管理者只写派工单、收证据、做只读核验、归档关闭。

## 本次修复的纠正路径

v1.2.0 的修复（即记录本段文字的这次）改为：**Codex max 独立审查出具发现清单 → 委派 subagent 执行者实施修改 → 管理者只读核验**（复跑发布门禁、`git diff --check`、核对文件内容），验收结论依据独立核验证据，而非执行者自报。
